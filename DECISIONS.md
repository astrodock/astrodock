# Decisions log — autonomous build

This file records the decisions I (Claude) made while building Astrodock end-to-end in one
unattended pass, per the request to "make major decisions on your own, but document what they
were along with the options and the path you chose." Everything here is **revisitable** — none
of it is locked. Each entry lists the options, the path chosen, and the rationale.

The decisions marked **OPEN** in `BUILD_PLAN.md` / `OPEN_SOURCE.md` are resolved at the top;
implementation-level decisions I had to make to get a working build follow.

---

## A. Previously-open decisions (from BUILD_PLAN.md "Open decisions")

### A1. License → **MIT**
- **Options:** MIT (simplest, most permissive) vs Apache-2.0 (adds an explicit patent grant).
- **Chosen:** MIT.
- **Why:** The plan recommends MIT "unless there's a reason." There's no patent strategy that
  argues for Apache-2.0 here, and MIT maximizes adoption for a self-host tool. Bundled
  components stay permissive (Postgres = PostgreSQL license; SeaweedFS = Apache-2.0; Caddy =
  Apache-2.0), so no copyleft contamination. Easy to relicense to Apache-2.0 later if a
  patent grant becomes desirable.

### A2. Postgres layer → **Drizzle ORM** (with the `postgres` / postgres.js driver)
- **Options:** Drizzle (SQL-first, light migrations) vs Prisma (heavier, codegen, separate engine).
- **Chosen:** Drizzle + postgres.js.
- **Why:** Recommended by the plan; SQL-first fits a tool whose whole point is "it's just
  Postgres," no separate query engine/binary to ship in the container, trivial to read the
  generated SQL. Migrations are plain `.sql` files generated by `drizzle-kit`, checked in.

### A3. Internal backups → **local-only for v1, with a documented off-box hook**
- **Options:** local-only (single box) vs optional off-box to an external object store.
- **Chosen:** Ship a `scripts/backup.sh` that does `pg_dump` of the control-plane DB + every
  internal app DB and snapshots the object-store data into the `objectdata` volume / a local
  dir. Document (loudly) the single-box caveat and leave a clearly-marked hook for pushing the
  backup tarball to an external S3 bucket (env-gated, off by default).
- **Why:** Keeps "zero external deps" true by default; the one place an external dep earns its
  keep (durability) is offered but never required. Off-box upload is a few lines the operator
  enables, not core machinery.

### A4. Custom domains per app → ~~deferred (post-v1)~~ **built** _(amended 2026-08-14)_
- Originally deferred. Built in Stage 16: Caddy on-demand TLS with a control-plane `ask`
  endpoint, the add → verify → activate flow, and DNS-drift checks in the health loop.
- Original rationale, kept for the record: the `subdomain` model is implemented; custom
  domains are additive and not needed for the core loop.

### A5. Non-GitHub deploy (CLI push of a local build) → ~~deferred (post-v1)~~ **built** _(amended 2026-08-14)_
- Originally deferred. Built in hardening pass #12: `astrodock deploy --local` tars the
  working dir (excluding `node_modules`/`dist`/`.env`) and hands it to the runner beside the
  "git clone" source, exactly the seam the deploy worker was structured to leave open.

### A6. Terminal endpoint → **gated behind `ASTRODOCK_ENABLE_TERMINAL` (default OFF)**
- **Options:** keep always-on vs gate behind an env flag.
- **Chosen:** The `/exec` SSE terminal is ported but registered only when
  `ASTRODOCK_ENABLE_TERMINAL=true`. Default off. Documented as arbitrary-RCE-by-design in
  `SECURITY.md`.
- **Why:** It's the single sharpest edge. Off-by-default is the responsible publishing posture;
  the trusted single operator can opt in.
- **Built (2026-09-06), and not where the precursor put it.** This decision sat unimplemented
  for months while the docs described it as done; `app-ops.js` had replaced it with named
  actions instead. What settled it was an app that crash-looped 809 times with no way to find
  out why. Four further choices, all deliberate:
  - **On the runner, not the control plane.** The precursor ran `sh -c` in the API container,
    which loads the key that decrypts every app's secrets — and could not read the app files it
    was aimed at, because those live on the runner. Running it on the runner fixes both.
  - **As the app's own user, with the app's own environment.** A shell is then no more powerful
    than the app it belongs to.
  - **Command-and-stream over SSE, not a pty.** No native dependency, no session lifecycle. It
    does not run `vim`; it was never `vim` that was needed.
  - **`exec` scope, plus masked output and an audit event per command.** `exec` is sensitive, in
    no preset, and absent from the operator role, so this is admin and owner. `runDeclared`
    stays the everyday path; the terminal is the escape hatch.

### A7. Name → **keep Astrodock** (working name, unchanged)
- No reason surfaced to revisit during the build. Env prefix `ASTRODOCK_`, CLI `astrodock`
  (alias `adock`), npm scope `@astrodock`, as locked.

### A8. Agent doc conventions → **`AGENTS.md` as source of truth + thin `CLAUDE.md` pointer**
- Both are emitted into every new app by the starter template. The contract itself now lives
  in the docs repo, served at `docs.astrodock.ai/AGENTS.md` and `/building-apps.md`; the root
  `AGENTS.md` here is a pointer to it.
- **Why:** `AGENTS.md` is the emerging cross-agent convention; a 3-line `CLAUDE.md` that points
  at it avoids drift while still being picked up by Claude Code specifically.

### A9. npm scope → **`@astrodock/*`, unpublished/vendored for now**
- Packages are named `@astrodock/*` with `"private": true` (workspace-internal). Nothing is
  published to npm during this build (not authorized, and not needed to run the stack).

## B. Implementation decisions (made to reach a working build)

> **Update (hardening pass):** B1 and B3 below were revisited and fully resolved — the runner is
> now its own container, and internal storage now mints per-app scoped keys. See the "Hardening
> pass" section in `BUILD_NOTES.md` for the full list of flaw fixes and live verification.

### B1. Runner topology → ~~merged into `api` for v1~~ → **SPLIT into its own container (resolved)**
- **Options:** (a) separate `runner` container from day one; (b) merge runner into `api`,
  split later.
- **Chosen:** (b). The spec explicitly allows this ("May be merged into `api` for a minimal
  deployment"). The `api` image installs git + the Docker CLI + PM2; Node buildpack apps run as
  PM2 processes inside it; Dockerfile apps run as sibling containers via the mounted Docker
  socket. All runner logic lives under `apps/control-plane/src/runner/` so it can be lifted into
  its own service later with no behavior change.
- **Why:** One fewer container to wire up to get a real end-to-end deploy working in this pass;
  the split is a packaging change, not a redesign.

### B2. Caddy dynamic reconfiguration → **Caddy Admin API `POST /load` with the Caddyfile adapter**
- **Options:** (a) write a Caddyfile to a shared volume + `caddy reload` (needs a shell into the
  caddy container or sudo, like the old SV code); (b) generate native JSON and PATCH the admin
  API; (c) generate a Caddyfile string and POST it to `http://caddy:2019/load` with
  `Content-Type: text/caddyfile`.
- **Chosen:** (c). The control plane regenerates the full Caddyfile from all apps and POSTs it to
  the Caddy admin API over the compose network. No shared-file race, no sudo, no shelling into
  another container.
- **Why:** Cleanest container-native approach; keeps the human-readable Caddyfile format from the
  old code; reload is atomic and zero-downtime. The admin API is bound to the internal network
  only (documented as a trusted-network surface).

### B3. Internal object-storage isolation → ~~shared key + prefix (v1)~~ → **per-app scoped keys (resolved)**
> Resolved in the hardening pass: each internal-storage app now gets its own bucket + an S3
> identity scoped to that bucket (minted in SeaweedFS via the runner). Cross-bucket access is
> denied (verified). Falls back to the original shared-key + prefix only if a scoped identity
> can't be minted. The original v1 rationale is kept below for context.

#### (original B3 — shared bucket + per-app prefix + shared platform key)
- **Options:** (a) provision a truly scoped S3 access key per app in SeaweedFS (faithful to the
  spec's "scoped key"); (b) one shared bucket, per-app key *prefix*, single platform-managed
  access key injected to every internal-storage app.
- **Chosen:** (b) for v1. The injected env var set is identical either way
  (`ASTRODOCK_STORAGE_ACCESS_KEY/SECRET_KEY/BUCKET/PREFIX/ENDPOINT/REGION`), so **app code never
  changes** when this is upgraded. The provisioner is an interface (`provisionStorage(app)`)
  with the per-app-key implementation droppable in later.
- **Why:** Dynamically minting scoped SeaweedFS identities at runtime from the Node control plane
  (via the weed shell / filer config) is fiddly and untestable in this environment. Per-prefix
  isolation matches the "fine, not fantastic" framing for the internal option; hard isolation is
  the documented reason to choose **external** storage or a future enhancement. **This is the
  most significant fidelity gap vs. the spec — flagged for review.** See `SECURITY.md`.

### B4. `ASTRODOCK_DATABASE_ENGINE` for external DB → **assume `postgres`**
- The spec says the engine var is "auto" and present whenever `database ≠ none`. For internal
  it's unambiguously `postgres`. For external I inject `postgres` too, since the documented
  graduation path is internal Postgres → Neon/Supabase/RDS (all Postgres). Apps that point at a
  non-Postgres external DB have the full `ASTRODOCK_DATABASE_URL` anyway and rarely read the
  engine var. Cheap to make this a per-app override later.

### B5. Env-var storage model → **one `app_env_vars` table for both declared vars and external-required reserved vars**
- App-declared vars (from `app.json` `env[]`) are stored as rows with their declaration metadata
  (`secret`, `required`, `default`, `description`) and an optional set value.
- External-mode reserved vars that need an operator value (`ASTRODOCK_DATABASE_URL`,
  `ASTRODOCK_STORAGE_*`) are stored as rows too, marked `kind = 'reserved'`, so the
  required-variable gate and the admin "set secret" UI treat them uniformly.
- Platform-*generated* secrets (`app_secret`, `app_jwt_secret`, internal DB password, internal
  storage key) live as columns on the `apps` row — they're never operator-edited.
- **Why:** A single uniform "things that need values" surface for the gate and the UI, while
  generated secrets stay out of the user-editable space. Replaces the old flat `envVars` array +
  `isSystem` flag.

### B6. Reserved env injection is computed at deploy, not stored
- The "auto" reserved vars (`ASTRODOCK_APP_SLUG/NAME/URL/BASE_DOMAIN/PORT/ENV`, internal
  `DATABASE_URL`, internal `STORAGE_*`) are recomputed from the app's modes + stack config on
  every deploy and written to the app's runtime env file / container `--env-file`. They are
  never persisted as editable rows, so they can't drift. The single documented unprefixed alias
  `PORT = ASTRODOCK_PORT` is added last.

### B7. Password hashing & admin auth → **unchanged from SV** (bcryptjs, 12 rounds; single `ADMIN_JWT_SECRET`, 8h bearer)
- Ported as-is; documented in the threat model. Not worth re-architecting for v1.

### B8. Scoped API tokens → **`tk_`-prefixed, SHA-256-hashed at rest, scope list**
- New `api_tokens` table: `id, name, token_hash, scopes[], last_used_at, created_at`. The raw
  token is shown once at creation. Middleware accepts an admin JWT **or** a valid token whose
  scopes cover the route. Token scopes deliberately **exclude user management** (`users:*`) — an
  agent can manage apps/deploys/env/tokens-it-owns but not platform users.
- Format `tk_<base62>`; verified by hashing the presented token and looking up the hash.

### B9. Port assignment → **auto-assigned from 3101+, stored on the app**
- Control plane is 3100. Apps get the next free port ≥ 3101 (max existing + 1). `ASTRODOCK_PORT`
  is injected from this. Same scheme as SV; works for both PM2 (bind locally) and Docker
  (container listens, Caddy proxies `app-<slug>:<port>`).

### B10. TLS modes → **`ASTRODOCK_TLS_MODE = auto | internal | off`**
- `auto` (default): Caddy gets real Let's Encrypt certs for `*.<base-domain>` (prod).
- `internal`: Caddy's internal CA (local dev / private network, no public DNS).
- `off`: serve plain HTTP (bare-metal behind another proxy / quick local poke).
- The Caddyfile generator reads this from stack env so the same artifact works locally and in
  prod without code changes.

### B11. Verify behavior → **ported faithfully**, including the `appAccess` gate and `AuthLog` results
- `/verify` keeps the exact result codes (`SUCCESS`, `BAD_PASSWORD`, `USER_NOT_FOUND`,
  `INACTIVE_USER`, `NO_ACCESS`, `INVALID_APP_SECRET`, …) so the auth-client contract is
  unchanged. `AUTH_URL` injected to apps now points at the internal service address
  (`http://api:3100`) instead of `localhost`.

### B12. Testing strategy → **verify what's runnable here; document what needs Docker**
- I have Node + a local Postgres in this environment, so I wrote and ran smoke tests for: the
  `app.json` schema validator, the reserved-env computation + required-var gate (pure logic),
  the auth-client, and the control-plane `/verify` + admin flows against a real local Postgres.
- The full `docker compose up` stack (Caddy routing, SeaweedFS, the Docker-app runner path)
  could not be exercised end-to-end in the build sandbox. Those paths are implemented to spec and
  reviewed by reading, but are marked **unverified-in-sandbox** in `BUILD_NOTES.md`. This is the
  main thing to smoke-test on a real Docker host before trusting it.
