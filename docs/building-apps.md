# Building apps for Astrodock

The long-form companion to the root `AGENTS.md`. Read that first for the contract; this doc has
the full environment-variable catalog, worked examples for every app shape, and troubleshooting.

---

## App shapes

| Shape | Files | Served as |
|---|---|---|
| Frontend + server | `app/` (→ `app/dist/`) + `server/server.js` | static frontend + `/api/*` → server |
| Server-only | standalone `server.js` | `/api/*` → server (no static) |
| Frontend-only | standalone `package.json` (no server) | static frontend only |
| Docker (any runtime) | `Dockerfile` | whole subdomain → container on `ASTRODOCK_PORT` |

The runner auto-detects node shapes. For Docker, set `runtime.type: "docker"` and (optionally)
`runtime.dockerfile`.

---

## `app.json` field reference

| Field | Req | Notes |
|---|---|---|
| `schemaVersion` | yes | `"1"` |
| `slug` | yes | `^[a-z0-9-]+$`, immutable identity (process/container/DB name) |
| `name` | yes | display name |
| `description` | no | shown in the admin UI |
| `subdomain` | yes | `^[a-z0-9-]+$`; app served at `https://<subdomain>.<base-domain>` (mutable) |
| `source` | yes | the object must be present, even as `{}` — its fields are all optional |
| `source.branch` | no | default `main` |
| `source.repoPath` | no | subdir to deploy from (monorepos) |
| `source.githubRepo` | no | `owner/repo`; can also be set via CLI/admin |
| `runtime.type` | yes | `node` or `docker` |
| `runtime.buildCommand` | no | node only; default `npm run build` |
| `runtime.dockerfile` | no | docker only; default `Dockerfile` |
| `auth.mode` | yes | `platform` or `public` |
| `database.mode` | yes | `internal`, `external`, or `none` |
| `storage.mode` | yes | `internal`, `external`, or `none` |
| `env[]` | no | declared variable *names* + metadata (see below) |

`env[]` entries: `key` (UPPER_SNAKE_CASE, not `ASTRODOCK_*`), `secret` (bool), `required` (bool),
`default` (string, non-secret only), `description`.

## Reserved `ASTRODOCK_*` environment catalog

The app **reads** these; it never sets or declares them. "auto" = generated by the platform;
"user-required" = an operator must set it before deploy (external modes).

| Variable | Present when | Source | Meaning |
|---|---|---|---|
| `ASTRODOCK_APP_SLUG` | always | auto | app slug / identity |
| `ASTRODOCK_APP_NAME` | always | auto | display name |
| `ASTRODOCK_APP_URL` | always | auto | public URL |
| `ASTRODOCK_BASE_DOMAIN` | always | auto | platform base domain |
| `ASTRODOCK_PORT` | always | auto | **the port the server MUST bind** |
| `ASTRODOCK_ENV` | always | auto | deploy environment (e.g. `production`) |
| `ASTRODOCK_DATABASE_URL` | database≠none | auto (internal) / user-required (external) | connection string (same name both modes) |
| `ASTRODOCK_DATABASE_ENGINE` | database≠none | auto | `postgres` |
| `ASTRODOCK_STORAGE_ENDPOINT` | storage≠none | auto / user-required | S3 endpoint |
| `ASTRODOCK_STORAGE_REGION` | storage≠none | auto / user-required | S3 region |
| `ASTRODOCK_STORAGE_BUCKET` | storage≠none | auto / user-required | bucket |
| `ASTRODOCK_STORAGE_PREFIX` | storage=internal | auto | per-app key prefix |
| `ASTRODOCK_STORAGE_ACCESS_KEY` | storage≠none | auto / user-required | S3 access key |
| `ASTRODOCK_STORAGE_SECRET_KEY` | storage≠none | auto / user-required | S3 secret key |
| `ASTRODOCK_AUTHORIZE_URL` | auth=platform | auto | **send the browser here to sign in** (public, on `auth.<base-domain>`) |
| `ASTRODOCK_LOGOUT_URL` | auth=platform | auto | ends the **platform** session — see below; it cannot sign a user out of your app |
| `ASTRODOCK_AUTH_URL` | auth=platform | auto | internal base for the server-to-server code exchange (`POST /token`) — not browser-reachable |
| `ASTRODOCK_APP_ID` | auth=platform | auto | = slug |
| `ASTRODOCK_APP_SECRET` | auth=platform | auto | proves your server is the app, when exchanging a code |
| `ASTRODOCK_APP_JWT_SECRET` | auth=platform | auto | sign your own sessions with this |

Plus the one documented unprefixed alias: `PORT = ASTRODOCK_PORT`.

**Why one name for internal & external:** `ASTRODOCK_DATABASE_URL` and the `ASTRODOCK_STORAGE_*`
set have identical names whether the resource is internal or external. The app reads one variable
and never knows the difference; graduating internal→external is a value change, not a code change.

## Worked examples

### A. Internal everything (the easy path)
```json
{ "schemaVersion":"1","slug":"notes","name":"Notes","subdomain":"notes",
  "source":{"branch":"main"},"runtime":{"type":"node"},
  "auth":{"mode":"platform"},"database":{"mode":"internal"},"storage":{"mode":"internal"} }
```
Postgres DB + storage prefix auto-provisioned and injected. Connect a repo, `astrodock deploy:watch`.

### B. External DB + external storage (heavier path)
```json
{ "schemaVersion":"1","slug":"crm","name":"CRM","subdomain":"crm",
  "source":{"branch":"main"},"runtime":{"type":"node","buildCommand":"npm run build"},
  "auth":{"mode":"platform"},"database":{"mode":"external"},"storage":{"mode":"external"} }
```
Deploy is blocked until you set the creds:
```bash
astrodock set-secret ASTRODOCK_DATABASE_URL 'postgresql://…@neon…'
astrodock set-secret ASTRODOCK_STORAGE_ENDPOINT 'https://…r2.cloudflarestorage.com'
astrodock set-secret ASTRODOCK_STORAGE_ACCESS_KEY '…'   # + REGION / BUCKET / SECRET_KEY
```

### C. Static-only, public (no server, no auth)
```json
{ "schemaVersion":"1","slug":"landing","name":"Landing","subdomain":"hello",
  "source":{"branch":"main"},"runtime":{"type":"node","buildCommand":"npm run build"},
  "auth":{"mode":"public"},"database":{"mode":"none"},"storage":{"mode":"none"} }
```

### D. Dockerfile app (any runtime)
```json
{ "schemaVersion":"1","slug":"py-tool","name":"Python Tool","subdomain":"pytool",
  "source":{"branch":"main","repoPath":"service"},
  "runtime":{"type":"docker","dockerfile":"Dockerfile"},
  "auth":{"mode":"platform"},"database":{"mode":"internal"},"storage":{"mode":"none"},
  "env":[{"key":"WORKERS","required":false,"default":"2"}] }
```
The container must listen on `ASTRODOCK_PORT` and answer `GET /health`.

## Using the injected resources

**Database** (Postgres, internal or external — same code):
```js
import postgres from 'postgres';
const sql = postgres(process.env.ASTRODOCK_DATABASE_URL);
```

**Object storage** (S3 SDK, internal or external — same code):
```js
import { S3Client } from '@aws-sdk/client-s3';
const s3 = new S3Client({
  endpoint: process.env.ASTRODOCK_STORAGE_ENDPOINT,
  region: process.env.ASTRODOCK_STORAGE_REGION,
  credentials: { accessKeyId: process.env.ASTRODOCK_STORAGE_ACCESS_KEY, secretAccessKey: process.env.ASTRODOCK_STORAGE_SECRET_KEY },
  forcePathStyle: true
});
// scope your keys under process.env.ASTRODOCK_STORAGE_PREFIX when storage is internal
```

**Auth** — see the root `AGENTS.md` §5 and `examples/starter-app/server/server.js`.

Two URLs, because two different things reach them. `ASTRODOCK_AUTHORIZE_URL` is followed by the
**user's browser**, so it is public and lives on `auth.<base-domain>`. `ASTRODOCK_AUTH_URL` is
where **your server** exchanges the returned code, and is an internal address that never leaves
the box. Using the internal one for the redirect sends your users to a hostname only Docker can
resolve.

```js
const { AstrodockAuth } = require('@astrodock/auth-client');
const auth = new AstrodockAuth();          // reads both from the environment

app.get('/login', (req, res) => {
  const state = crypto.randomUUID();
  req.session.state = state;               // compare it on the way back
  res.redirect(auth.authorizeUrl({ redirectUri: CALLBACK, state }));
});

app.get('/callback', async (req, res) => {
  if (req.query.state !== req.session.state) return res.status(400).send('bad state');
  const user = await auth.exchange(req.query.code, { redirectUri: CALLBACK });
  // user = { userId, email, name } — now mint your OWN session
});
```

**Register your callback first.** The platform only redirects to URLs registered for the app
(admin → the app → Sign-in). An unregistered `redirect_uri` is refused before anyone is sent
anywhere, which is what stops a stolen code being delivered somewhere it should not go.

**Signing out is not symmetrical.** `ASTRODOCK_LOGOUT_URL` ends the platform session, so the
next app asks for a password again — but it cannot touch your app's own session cookie, which
lives on your subdomain. For a "sign out everywhere" button: clear your own cookie, *then* redirect
there. Anything already signed in to another app stays signed in until that app's session expires.

**Signing in once covers every app.** A user who has signed into one of your apps is redirected
straight back from the next one without a prompt. Add `prompt=login` to the authorize URL if your
app needs proof of presence before something consequential.

## Deploy & observe

```bash
export ASTRODOCK_URL=https://admin.example.com
export ASTRODOCK_TOKEN=tk_...          # scoped token (admin UI → Tokens)

astrodock apply                         # create/connect/provision from app.json
astrodock set-secret OPENAI_API_KEY     # (reads value from stdin)
astrodock deploy:watch                  # deploy + stream log to terminal status
astrodock logs --lines 200
astrodock status
```

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `deploy` returns "Missing required variables" | Set them: `astrodock set-secret KEY`. External DB/storage creds + `required` declared vars all gate the deploy. |
| App 502s after deploy | Server isn't binding `ASTRODOCK_PORT`, or crashed — check `astrodock logs`. |
| `/api/...` 404s | Server routes must be under `/api`; Caddy only proxies `/api/*` to the server. |
| Login returns 403 | The user hasn't been granted access to this app's slug (admin UI → Users). |
| Frontend loads but blank | `buildCommand` didn't produce `app/dist/` — check the deploy log. |
| Health probe never healthy | Add `GET /health` → 200. |
| Docker app unreachable | Container must listen on `ASTRODOCK_PORT` and be the foreground process. |
